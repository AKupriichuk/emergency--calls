## Stage 1 — Design

### 1.1 Table schema

Single table `emergency_calls`:

| column | type | required | notes |
|---|---|---|---|
| `id` | `UUID` | yes (server-generated) | primary key; generated by the service (`uuid4`), never accepted from the client |
| `call_number` | `VARCHAR(50)` | yes | dispatch call number/code, free-form |
| `urgency_category` | `SMALLINT` | yes | must be `1..4`; indexed — it is the list filter field |
| `address` | `TEXT` | yes | incident address, free-form, unbounded length |
| `received_at` | `TIMESTAMPTZ` | yes | when the call was received |
| `arrived_at` | `TIMESTAMPTZ` | yes | when the crew arrived; must be `> received_at` |
| `outcome` | `VARCHAR(255)` | yes | outcome/result of the call |

Index: `ix_emergency_calls_urgency_category` (btree) on `urgency_category`, since it is the
only field the list endpoint filters on.

Type rationale:
- `id` is a `UUID` rather than an auto-increment integer specifically because the client must
  never be able to supply or guess it, and a server/DB-generated UUID removes any incentive to
  accept a client-provided value.
- `urgency_category` is `SMALLINT`, not `INTEGER`, because its domain is the four values `1..4`
  — no reason to reserve 4 bytes for it.
- `received_at`/`arrived_at` are `TIMESTAMPTZ`, not naive `TIMESTAMP`, because the validation
  rule `arrived_at > received_at` must hold regardless of the timezone the client sends values
  in; storing the offset avoids silently comparing two different wall-clock times.
- `call_number`/`outcome` are bounded `VARCHAR` because they are short codes/labels; `address`
  is `TEXT` because street addresses have no natural fixed cap.

No uniqueness constraint on `call_number`: the assignment does not require it, and dispatch
systems can legitimately reuse/reopen a call number.

### 1.2 API

Pagination defaults (list endpoint): `limit` defaults to **50**, maximum **200**; `offset`
defaults to **0**. Both are validated (non-negative integers, `limit` within bounds) and
rejected with `400` otherwise. List is ordered by `id` for stable pagination.

Every `400` response body has the shape `{"error": "<message>", "field": "<field name or null>"}`.
A malformed `id` path parameter (not a valid UUID) is treated as a validation error → `400`,
not `404` — it never reaches the database layer.

| # | Endpoint | Method | Request body | Success | Error responses |
|---|---|---|---|---|---|
| 1 | `/emergency-calls` | `POST` | `{call_number, urgency_category, address, received_at, arrived_at, outcome}` | `201` + created record (incl. `id`) | `400` missing/invalid field, `urgency_category` outside `1..4`, `arrived_at <= received_at` |
| 2 | `/emergency-calls` | `GET` | query: `limit`, `offset`, `urgency_category` (optional filter) | `200` `{items: [...], total, limit, offset}` | `400` invalid `limit`/`offset`/`urgency_category` value |
| 3 | `/emergency-calls/{id}` | `GET` | — | `200` record | `404` not found, `400` malformed `id` |
| 4 | `/emergency-calls/{id}` | `PUT` | full record body (same shape as POST, no `id`) | `200` updated record | `404` not found, `400` invalid body or malformed `id` |
| 5 | `/emergency-calls/{id}` | `DELETE` | — | `204` no content | `404` not found or already deleted, `400` malformed `id` |
| 6 | `/healthz` | `GET` | — | `200` `{"status": "ok"}` when `SELECT 1` succeeds | `503` `{"status": "unavailable"}` when the DB check fails |

A second `DELETE` on an already-deleted `id` returns `404`, not `204` — the service does not
treat delete as idempotent.

Any unhandled database/ORM error is caught at the service boundary and turned into a generic
`500 {"error": "internal server error"}` — the raw exception never reaches the client.
